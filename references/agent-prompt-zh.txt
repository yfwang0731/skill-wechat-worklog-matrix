# 需求识别子代理提示词模板（发给并行 agent，每 agent 一份 + 各自的文件清单）

> 使用说明：把 {{...}} 占位符替换为 config.json 中对应值后再发给子代理。
> 必填：{{处理人}}(←people.handler) {{我方标识}}(←people.my_identifiers) {{服务对象}}(←people.service_object) {{业务系统描述}}(←excel.business_system_description) {{对方关键字}}(←people.counterparty_keyword)
> 可选：service_object / business_system_description 在 config 缺失时，由执行代理据用户描述补充后再发。
> 规则开关：下发前按 config.json rules.* 把【判断规则】默认句替换为下方【开关渲染表】对应句（默认全开=保持现文）。

你在帮系统运维工程师【{{处理人}}】把微信聊天记录整理成"需求跟踪矩阵"。
【{{处理人}}】的服务对象是【{{服务对象}}】，其使用的业务系统为：{{业务系统描述}}。
对方员工通过微信单聊或群聊向他提系统问题 / 改数据 / 优化 / 新需求。

【输入文件】（逐行读取，每行格式：`日期 时间 | 发送者 | 内容`）：
<在此列出分配给你的转录文件绝对路径>

【人物】发送者为 {{我方标识}} 之一 = 我方（{{处理人}}）；其余 = 对方（需求提出方）。
群内发送者已是解析后的成员名（可能含岗位词），解析不出则是原始 ID。

【判断规则】
1. 只记**对方提出的、针对系统的需求**（改数据/报错/bug/优化/新功能/答疑等）；寒暄/闲聊/通知/纯图片往来不算。
   需求**必须可交付** —— 能落成一句"改什么 / 修什么 / 加什么"。只表达体感或情绪、指不出具体对象的，不是需求（见下条）。
2. 答复判定（在会话内找我方对该需求的回复）：
   ⚠️ **你看不到全部会话**（转录按会话分包给你，别人手上还有别的会话）：如果一条需求
   可能在其他会话里被答复过，**不要因为"本会话看不到回复"就丢掉它** —— 拿不准时宁可
   输出该行、把结果记为最保守的值，让人在裁决阶段划掉，也不要静默漏掉一条真需求。
   - 我方明确拒绝（"不能做/做不了/没法/不支持/不行/不处理/你们自己改"等）→ 忽略，不输出。
   - 提出后我方**无任何实质回复** → 忽略（**但数据修改类例外 —— 见本节下面那条"数据修改类特例"，它优先于本条**）。
   - **笼统抱怨不算需求**（`rules.ignore_vague_complaints`）：只表达体感/情绪、**指不出具体对象**的反馈
     （"系统特别卡 / 太慢了 / 又出问题了 / 不好用"），**且我方未明确答复已解决** → 忽略，不输出。
     反之，对方给出了**可定位对象或量化现象**（哪个功能 / 哪一步操作 / 哪个单据，或"搜一个箱号要等15秒"
     "审批后卡住"），仍按 bug 正常记。
   - 我方明确说完成（"好了/已完成/改好了/可以了/搞定/处理好了/能用了/你试试"等）→ 输出，
     outcome="done"，v_date=w_date=我方说完成那条消息的日期。
     ⚠️ 判定"已解决"时，**运维性动作与安抚不算完成**：重启系统 / 稍后看 / 换个浏览器 / 清缓存 /
     再看看 / 我看看 —— 这些不是"改好了"，不得据此把 outcome 记为 done。
   - **数据修改类特例**（请直接改数据：改费用/改结算单位/改单号箱号/录补调数据/导数据等）：
     没说完成也没拒绝（如只回"我看看/下午弄/等下/好"或直接去做了没说结果）→ 默认完成，
     outcome="default_done"，v_date=w_date=**对方提出消息的日期**；若明确拒绝→忽略。
     ⚠️ **本条优先于上面那条"无实质回复→忽略"**：数据修改类即使我方**一句话都没回**，
     也按本条处理（默认完成）。这类需求大多是"直接去做、不回报结果"，若按"无回复"丢掉
     会整批漏记。两条规则的重叠处以此为准（`rules.data_change_default_done=false` 时改为
     outcome="pending" 照常输出，同样不走"无回复→忽略"）。
   - 一条消息含多个需求→拆成多行。同一需求后续被对方催/重提：已按完成处理过则不新增；
     之前被忽略（拒绝/无回复）后重提且本次有结果→新增一行。

3. 描述 L：一句话简略描述，带关键业务对象（单号/箱号/提单号/票号/功能名 + 改什么）。
   参考风格："ANTSQCY250789019 错误数据处理"、"锁帐时间调整到15号"、
   "付款申请更改核销金额时，增加不允许点击申请主体表保存按钮的控制"。
   **L 只写业务内容，不要写判定依据/分析过程**。
4. Q 归类：**只能取这 5 个值之一，照抄不要改写、不要连写**（如不要写"优化或需求"）：
   改数据→`数据处理`；功能/界面/流程**新增**→`需求`；已有功能/界面的**改进**→`优化`；
   系统出错→`bug`；仅查证问询→`答疑`。
   R=高/中/低（批量改数/财务/锁账/全局功能=高，琐碎=低，中间=中）；S=优先级 1-5 估算，不确定留空。
5. O=提出人姓名（备注形如"{{对方关键字}} X 岗位"取 X，去掉前缀/括号后缀）；N=岗位词（如商务经理/客服/
   财务/调度/操作等）看不出留空；群内解析不出的 O=原始 ID 并在 note 注明。
6. 群内同一需求多人先后提及/附和：只记最早提出人一条。

【开关渲染表】下发前按 config.json rules.* 逐项确认；值为 false 时把上面【判断规则】里对应的默认句替换为下列"关"态句（关态记下的行需人工裁决是否最终保留）：
| 开关 | 开（默认=现文） | 关 |
| rules.ignore_if_rejected | 我方明确拒绝 → 忽略，不输出 | 仍输出该行，outcome="rejected"，note 注明"我方已明确拒绝，待人工裁决"，v_date=w_date=提出日期 |
| rules.ignore_if_no_reply | 提出后无实质回复 → 忽略 | 仍输出该行，outcome="no_reply"，note 注明"我方无回复，待跟进/人工裁决"，v_date=w_date=提出日期 |
| rules.ignore_vague_complaints | 笼统抱怨（指不出具体对象）且我方未明确答复已解决 → 忽略 | 仍输出该行，outcome="vague"，note 注明"笼统抱怨，待人工裁决"，v_date=w_date=提出日期 |
| rules.data_change_default_done | 数据修改类无完成无拒绝 → 默认完成 | 不默认完成，outcome="pending"，note 注明"未确认完成，待人工裁决"，v_date=w_date=提出日期 |
> 其余开关不入本提示词：rules.reuse_position_column 决定是否跑 position_reuse；merge_cross_session / similarity_threshold / near_days / people.counterparty_keyword 由 build_matrix_rows 代码读取。

【输出】把结果 JSON 写入文件：<out.json>
格式为数组：
[{"chat":"文件名","O":"姓名或ID","N":"岗位或空","ask_date":"YYYY-MM-DD","L":"描述",
  "Q":"数据处理|优化|需求|bug|答疑","R":"高|中|低|空","S":"1-5|空",
  "outcome":"done|default_done|rejected|no_reply|vague|pending","v_date":"YYYY-MM-DD","w_date":"YYYY-MM-DD",
  "evidence":"关键原文含时间，最多两段（用于人工复核）",
  "note":"业务性补充；禁止写规则判定理由"}]
只写要计入矩阵的行（被忽略的不写）。完成后回复：输出行数 + 每行摘要(O|L|outcome|date)。
